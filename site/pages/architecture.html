Architecture

A system controller owns the screen, the keys and the network. Modules are separate programs it starts one at a time and talks to over a small, versioned API.

The system controller

The controller runs as a system service and is the only program that touches the hardware. It draws the left icon strip, Home and Settings, routes key presses to the module in front, keeps each module's data and saves, and applies network settings. It also serves the panel shell to the kiosk browser and the web view to the network.

Modules

A module is a Node.js program plus web pages for its UI. The controller starts it as a child process and talks to it with JSON-RPC 2.0 over a Unix socket, one message per line (module API v1). A module gets:

  • Keys: labels, colours and images for all 15 keys, and press, release and hold events.
  • UI pages: HTML shown on the panel, and optionally fuller pages in the web view. Pages talk to their module through window.rcs and can use the system elements (<rcs-button>, <rcs-tile>, <rcs-field> and more), which follow the system theme.
  • State, config and saves: the module's own settings and presets, autosaved and restored after a restart. Live device state is never stored; the module reads it from the device again.

Only one module runs at a time. Home leaves it running in the background; starting another one stops it. If a module crashes, the controller restarts it once and tells you; if it crashes again, it stays stopped.

Panel and web view

The panel is a kiosk browser showing the controller's shell, which frames the module's page. The web view serves the same data to any browser: a mirror of the panel you can tap, plus the module's own web pages. Both stay in step because the data lives in the controller, but browsing the web view never moves the panel.

Distribution and updates

  • Modules ship as <id>-<version>.zip with an Ed25519 signature, from GitHub Releases in each module's own repo. The module index lists each module once, with its publisher key.
  • The controller ships as a signed release in rcs-releases. A unit unpacks a new version beside the running one and switches over; if the new version fails to start twice, it rolls back.
  • Units check at boot and once a day, show what is available, and never install on their own.
