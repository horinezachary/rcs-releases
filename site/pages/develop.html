Develop a module

A module is a small TypeScript or JavaScript program with web pages for its UI. You build it against a desktop simulator, then publish signed releases from your own GitHub repo.

The module SDK, the project template and the simulator are not on npm yet; the package names on this page (@rcs/module-sdk and the rest) are placeholders until the platform opens to outside developers. Today, module repos link the SDK from a checkout of the main source repo, which is private, so building a module currently needs access to it; access is by invitation for now.

llms.txt sums this page up for AI coding tools.

Start a module

# with access to the source repo, next to your module's folder
git clone https://github.com/horinezachary/rack-control-surface
cd rack-control-surface && npm install && npm run build
node packages/create-rcs-module/bin.js ../rcs-my-module
cd ../rcs-my-module
npm install        # links the SDK from ../rack-control-surface
npm run dev        # the simulator, with your module loaded and reloaded on save

The simulator runs the real controller: the panel and the 15 keys in a browser at :5173/sim, the web view at :5174, with controls to crash the module or cut the power so you can test recovery. The new repo has tests against a fake controller (npm test), a release workflow, and an AGENTS.md with the rules below for AI coding tools.

What a module looks like

import { defineModule } from '@rcs/module-sdk';

export default defineModule({
  async start(ctx) {
    await ctx.state.init({ count: 0 });
    await ctx.keys.setMany([{ index: 0, label: '+1' }]);
  },
  key(ctx, e) {
    if (e.index === 0 && e.action === 'down') {
      void ctx.state.patch({ count: ctx.state.value.count + 1 });
    }
  }
});
  • module.json names the module, its version, the API version, its entry file, its panel UI folder and, optionally, web view pages and a colour scheme.
  • ctx.state holds the module's own data and is autosaved. ctx.config holds its settings. ctx.secrets holds logins and API keys, which never reach a page.
  • ctx.keys draws the keys; key and hold receive presses. ctx.strip sets the module's icons in the left strip.
  • ctx.ui.send talks to your pages, which answer with rcs.send and listen with rcs.on('message'). Pages can use the system elements (<rcs-button>, <rcs-tile>, <rcs-field>, <rcs-dialog> and more).
  • ctx.status shows the connection on Home and in the web view; ctx.verifyPin asks the operator for the PIN before something sensitive.

Rules every module follows

  • The device is the source of truth. State and saves hold only your module's settings and presets, never the device's live state (for example a router's current routes). Read it from the device after starting and after every reconnect.
  • Starting, restoring and reconnecting only read. Commands go to equipment only when an operator taps something. Modules that control live gear have an Allow controls switch, off by default, and ask for a second press or a confirmation before a command.
  • Logins go in secrets, never in state, config or files.
  • Other modules run beside yours. In the background your module keeps polling and updating its state, but doesn't get the keys or the screen. Don't count on having the unit, or a local port, to yourself.
  • Pages render what the module sends. The panel and any number of browsers show the same data; navigation (page, tab, selection) stays in each page. Send a newly opened page the whole view at once.
  • Web pages scroll as one page. No fixed-height scroll boxes or full-window layouts; grids that fit a phone.
  • Develop against a simulator of your equipment, and only read from real show equipment until its owner says otherwise.
  • Use the system elements and theme for a consistent look; a module may set its own colour scheme.

Package and sign

node node_modules/@rcs/module-sdk/dist/pack-cli.js keygen   # once; writes rcs-signing.key, prints your public key
npm run pack                                                # release/<id>-<version>.zip
npm run sign                                                # release/<id>-<version>.zip.sig

Packages carry no node_modules: the unit provides the SDK, and anything else must be bundled into dist/. The template's release workflow runs on every merge to your default branch: the pull request's title picks the version (feat: minor, fix: patch), and it tests, packs, signs and publishes a GitHub Release tagged v<version>. It needs two Actions secrets: RCS_SIGNING_KEY (your private key; one per module) and RCS_SOURCE_TOKEN (read access to the source repo, to build the SDK).

Get listed

Open a pull request on rcs-releases that adds your module to index.json:

{
  "id": "my-module",
  "name": "My Module",
  "description": "What it controls, in one line",
  "repo": "you/rcs-my-module",
  "publicKey": "ed25519:…"
}

Once it's merged, units list your module, offer each new signed release as an update, and this site gets a page for it. Keep releases tagged v<version> with <id>-<version>.zip and its .zip.sig, and marked Latest: when GitHub's API limit is used up, units find the newest release through github.com by those names. To test on a unit before then, turn on Developer mode at the panel and upload an unsigned zip from the web view's Modules page.
